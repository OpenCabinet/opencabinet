# 0016 — A 3D view drawn with wgpu into an image

- **Status:** accepted
- **Date:** 2026-11-19, decided 2026-11-18
- **Deciders:** Andrés (@A-newGP)

## Context and problem statement

Cabinet shops sell and check their work by looking at it. Until now,
OpenCabinet Designer showed a project only as 2D drawings: elevations,
plans and the front of one cabinet. Andrés asked for a 3D view where the
whole room can be seen with real-looking materials, a cabinet opened on its
own with a double-click, and each of its parts selected to see its size,
material, edges, holes and hardware. How should the program draw in 3D,
inside its Slint window ([ADR-0012](0012-desktop-ui-toolkit.md)), without
breaking the promise to modest computers
([ADR-0014](0014-modest-hardware-budgets.md))?

## Decision drivers

- **Looks:** grain that follows each part, edges, holes, hardware and
  smooth edges, on screen at once.
- **Speed:** turning a kitchen of 30 cabinets must feel immediate.
- **Every computer still runs the program:** a computer without a usable
  graphics card must still open every other view, and should still show
  the 3D view, slower.
- **Size and build time** within ADR-0014: a small installer, a workspace
  that builds in minutes.
- **Licenses** compatible with GPL-3.0-or-later.
- **Testable in CI**, which has no graphics card.

## Considered options

1. **wgpu**, drawing into an image in memory that the window shows.
2. **Bevy**, a complete game engine, embedded in the window.
3. **OpenGL** directly, under Slint's own drawing.

## Decision outcome

Chosen: **option 1, wgpu into an image**, because it gives full control of
how a cabinet shop's parts look and stays small, while leaving the rest of
the window exactly as it is.

- A new crate, `opencabinet-view3d`, builds the scene (`scene`), moves the
  camera (`camera`) and draws (`render`). Only `render` touches the GPU,
  so building scenes and picking parts are tested on any computer.
- The evaluator gives every part its place in its product
  (`opencabinet_eval::assembly`), the transform RFC-0001 §9 foresaw, and a
  test checks that no two parts of the sample kitchen are in the same place
  except where a joint puts one into the other.
- wgpu draws into a texture of its own, multisampled four times when the
  adapter allows; the picture is read back and shown as a Slint image. The
  window keeps its own renderer, so nothing changes for the 2D views.
- wgpu tries the best adapter (Direct3D 12, Vulkan, Metal or OpenGL), then
  its **fallback adapter**, which draws on the processor: WARP on Windows,
  lavapipe or llvmpipe on Linux. Only when neither works does the 3D view
  say so; every other view still works.
- The renderer is made the first time a view shows 3D, once the window
  has given it a size. The window opens on the plan, so starting costs
  what it did before; a user who shows only drawings pays nothing for the
  3D view. Several views share one renderer, each with its own camera.
- Materials look as their names say (species, plywood, melamine and its
  color, MDF), drawn by the shader: grain, plies and floor planks are
  computed, not read from images. Materials that carry their own
  appearance, and photos of them, wait for a small RFC-0003 on material
  appearance, since RFC-0001 is accepted.
- Hardware is drawn as simple shapes: a hinge's cup and arm, slides under a
  drawer box, pins under a shelf. Dowels and confirmat screws are placed by
  the standard's joinery rules and drawn as wooden and steel rods, solid
  even in X-ray.

### Budgets for the 3D view

The 3D view is part of the program, but like the plan says of optional
features, it has budgets of its own and does not raise the base program's:

| Measure | Budget | On the reference computer |
| --- | --- | --- |
| Start-up and memory before a view shows 3D | Unchanged from ADR-0014 | The renderer is not made |
| A frame of a 30-cabinet kitchen, 1366 × 768, with a graphics card | 16 ms (60 per second) | Integrated graphics from about 2015 |
| The same frame drawn on the processor | 250 ms | Two cores, no graphics card |
| Building the scene after an edit | 20 ms | Processor only |
| Memory added once the 3D view is open | 150 MB | With either adapter |

CI checks that the sample kitchen is drawn, using lavapipe on Linux and
WARP on Windows, and keeps the pictures as artifacts; the release
measurements on a reference computer include these budgets.

### Consequences

- Good, because the program now shows what it builds, part by part, with
  its machining, and the same scene will show joinery and drawings later.
- Good, because the 2D views, exports and every other feature run exactly
  as before on any computer.
- Good, because placing parts in 3D also tests the evaluator: a part in
  the wrong place fails CI.
- Bad, because reading the picture back costs a copy per frame, which a
  shared texture would avoid; Slint's wgpu integration is still marked
  unstable, so this can change when it is not.
- Bad, because lighting, picking and materials are ours to write and keep.
- Neutral, because wgpu adds about 100 crates to the build, all under
  licenses cargo-deny already allows.

## Pros and cons of the options

### wgpu into an image

- Good, because it runs on every platform the program targets, with a
  fallback that needs no graphics card.
- Good, because it is MIT or Apache-2.0, actively maintained, and already a
  dependency Slint knows.
- Bad, because the picture is copied back to the processor each frame.

### Bevy

- Good, because lights, shadows and materials come with it.
- Bad, because it adds tens of megabytes and minutes of build time, changes
  between versions often, and its integration with Slint is experimental.

### OpenGL under Slint

- Good, because it is the simplest to connect.
- Bad, because drivers on Windows vary, macOS has abandoned it, and Slint's
  software renderer, used without a GPU, cannot host it.
